# KGP-001: KineGrant Core Authorization Protocol

Status: **KGP-001 Experimental Open Draft 0.1**
Date: **2026-08-10**

## 1. Problem

Existing systems separately describe data-use rights, connected-device actions,
robot middleware permissions, industrial roles, and smart-home access. They do
not provide one cross-domain object that an actuator can verify immediately
before a physical action and bind to a signed outcome afterward.

KineGrant introduces a narrow interoperability layer. It intentionally does not
define robot motion planning, identity enrollment, legal ownership, sensor
truth, or consensus.

## 2. Core objects

### 2.1 ActionRequest

An action request MUST contain:

- globally unique `request_id`;
- authenticated `agent` identifier;
- physical or cyber-physical `target` identifier;
- canonical `action` from the KineGrant action vocabulary when a strict
  vocabulary policy is in force (see [ACTION-VOCABULARY.md](ACTION-VOCABULARY.md));
- declared `purpose`;
- timezone-aware `issued_at`;
- optional, policy-visible `context`.

Its canonical SHA-256 digest binds later objects to the exact request.

### 2.2 PolicyRule

A rule contains an issuer, target pattern, `allow` or `deny` effect, actions,
subjects, purposes, constraints, and obligations. Engines MUST default to deny.
Draft 0.1 uses deny-overrides: any applicable denial defeats every applicable
allow rule. This deliberately sacrifices complex precedence for safe,
deterministic behavior.

An implementation MUST authenticate policy issuers independently of the policy
document. An unauthenticated source MUST NOT create an `allow`; it MAY add a
restriction or denial. Policy validity windows MUST be evaluated against the
engine's trusted clock, not the request's self-declared `issued_at`. Implementations
MUST reject stale or unreasonably future-dated requests.

Policy rules MAY impose physical constraints in addition to identity and time
checks: `max_force_newtons`, `max_velocity_mps`, and `allowed_zones`. When a
rule declares one of these constraints, the request MUST declare the matching
context value (`force_newtons`, `velocity_mps`, `zone`); a missing or
non-numeric declaration fails closed, and a zone outside the allowed set is
denied. For a `deny` rule, the same bound applies when evidence is missing or
the declared value exceeds the bound, so a physical ceiling cannot be bypassed
by omitting the measurement.

### 2.3 Decision

A decision records the request digest, outcome, reason, matched policy IDs,
obligations, and a digest of the complete normalized policy snapshot plus its
trusted-issuer set. A decision is evidence of evaluation, not permission by itself.

### 2.4 PhysicalActionCapability

Only an allowed decision can produce a capability. It MUST:

- be signed by a trusted authority;
- bind agent, target, action, purpose, request digest, and policy digest;
- include a random nonce;
- have a lifetime no longer than five minutes;
- be consumable once by default.

The gate MUST independently reject unknown versions or fields, invalid time order,
and capabilities whose half-open validity window `[not_before, expires_at)` exceeds
five minutes. Consumption MUST be an atomic consume-if-absent operation. Durable
deployments MUST preserve replay state across process and device restarts.

The reference implementation uses Ed25519 and RFC 8785 JCS (JavaScript Object
Notation Canonicalization Scheme) as the deterministic encoding for digests and
signatures. A later draft may additionally offer deterministic CBOR.

Draft v0.2 adds a scoped capability form that carries a target pattern, action
and purpose lists, physical constraints, and an approval tier. Scoped
capabilities can be attenuated (strictly narrowed) by the same issuer; see
[ATTENUATION.md](ATTENUATION.md). Every capability remains single-use and must
be verified by a local action gate.

Delegation to another agent is opt-in and bounded: a root capability may allow
up to three delegation hops, and every delegated capability binds one specific
delegate agent and the delegate's own request digest. Delegates cannot
re-delegate. The action gate verifies the executing agent against the bound
delegate.

Policy decisions carry a `required_approval_tier` (0 = automatic, 1 = operator
approval, 2 = human present) computed from the strongest `min_approval_tier`
constraint among the applicable allow rules.

Deployments SHOULD additionally enforce forbidden combinations: once a
dangerous set of actions has all been observed in the action journal, new
matching requests fail closed (see [SEQUENCE-POLICY.md](SEQUENCE-POLICY.md)).
Agents, targets, and policies SHOULD use the canonical
`urn:kinegrant:<kind>:<namespace>:<local-id>` identifiers defined in
[IDENTITY.md](IDENTITY.md).

### 2.5 ActionGate

The gate sits as close to the actuator as the platform permits. It MUST fail
closed when the signature, issuer, time window, request binding, or replay check
fails. Verifying a capability without gating the actuator is non-conforming.

### 2.6 PhysicalActionReceipt

The executor signs a single terminal receipt containing the capability ID, request digest,
result, time interval, optional evidence hash, and previous receipt hash. Raw
video, audio, location, or personal data SHOULD NOT be included. Receipts prove
what an executor attested; they do not alone prove physical truth.

Receipt verification MUST use a caller-controlled trusted-executor set when
authenticity, rather than only cryptographic integrity, is claimed. A receipt log
MUST reject a second terminal receipt for the same capability.

When the capability is a v0.2 scoped capability, the receipt MUST record its
approval tier, physical constraints, and parent capability id so the audit
trail shows the exact authorization context that was consumed. v0.1 receipts
remain unchanged.

## 3. Discovery

KineGrant does not mandate one discovery transport. A target MAY expose its identity
and policy pointer through W3C WoT, QR/fiducial marker, NFC, BLE, Matter, OPC UA,
or a trusted local registry. Discovery data MUST be authenticated before it can
grant a capability. Unauthenticated discovery MAY only add restrictions.

## 4. External policy profile

Adapters normalize external inputs. An adapter MUST reject authorization documents
containing constructs it cannot interpret; it MUST NOT silently convert an unknown
restriction into permission or drop an unparsable prohibition. Adapter output
records its source standard and profile. Caller-supplied context MUST NOT override
adapter-owned identity fields such as transport or profile.

## 5. Ledger integration

KineGrant's safety path is ledger-independent. Implementations MAY publish hashes of
identities, policy versions, revocations, or receipt batches to a public or
consortium ledger. A ledger confirmation MUST NOT be required for emergency stop
or other immediate safety controls.

## 6. Required security properties

- default deny;
- deny overrides;
- explicit trusted issuers;
- short capability lifetime;
- request binding;
- replay detection;
- signed, chained receipts;
- privacy-minimized evidence;
- fail-safe behavior when adapters or registries are unavailable.

## 7. Open questions

- policy conflict across legitimate co-owners;
- revocation during an already-running action;
- multi-agent actions requiring more than one capability at the same time;
- privacy-preserving target and subject discovery;
- hardware-backed keys and actuator attestation;
- semantics for emergency and accessibility overrides;
- formal verification of adapter behavior.
